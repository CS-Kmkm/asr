# Native capture startup returns RPC_E_DISCONNECTED

- Environment [stated]: Windows 11, isolated debug app `org.localvoice.input.issue87completion`, virtual input `name:CABLE Output (VB-Audio Virtual Cable)`, CPAL 0.15.3. The normal release app/profile was preserved.
- Symptom [stated]: two recording-start attempts reported `failed to build input stream` with HRESULT `0x80010108` before public audio playback. A fresh process later retained its start claim while the UI still showed ready; its exact wait point was not established. No successful recording/insertion measurement was published.
- Evidence [stated]: local `.ai/issue-87-completion-20261115/app-stderr-v{1,2}.log` and `native-run-v2/status.json`; the displayed startup error was observed through Windows UI Automation. The passive observer's hotkey-derived `recording` phase did not prove that microphone capture had started.
- Security boundary [stated]: security-software confirmation appeared during startup, and the user reported handling it. The agent did not operate that dialog. The dialog's causal role is unconfirmed; do not treat its appearance as proof that it caused the HRESULT.
- Cause [unresolved]: audio-client/device invalidation and startup waits remain under investigation. A process-wide enumerator/COM-lifetime explanation was considered but not established.
- Source facts [derived]: pinned CPAL `src/host/wasapi/device.rs` uses a process-wide `OnceLock<Enumerator>`; `com.rs` initializes COM as STA by default and balances successful initialization on thread teardown. These facts alone do not prove the cause of this incident.
- External semantics [stated]: [CoInitializeEx](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-coinitializeex) sets the calling thread's apartment and requires balancing successful calls. [CoIncrementMTAUsage](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-coincrementmtausage) can keep MTA resources alive without active MTA threads; this is a possible mechanism, not an adopted fix.
- Non-causes [derived]: the error occurs while building capture, before transcribing or pasting. It does not establish an ASR-accuracy, model-download or clipboard-restoration defect. Both new runtimes separately recognized the cached public clip on CUDA after integration; their metadata-only smoke reports are local siblings of this incident's evidence.
- Measurement rule [decision]: never play evaluation audio based only on receipt of a start shortcut. Verify actual app recording state first. Failed starts and observer desynchronization stay outside latency/CER/insertion-success statistics.
- Counterexample [stated]: on 2026-11-16 JST, `native_virtual_input_reopens_after_enumeration_thread_exits` passed on unmodified production audio code: enumeration on a short-lived thread, followed by two successful open/close cycles of the virtual cable (3.03 s). Log: `.ai/issue-87-completion-20261115/native-audio-probe-before-v1.log`. Short-lived enumeration alone is therefore not a sufficient reproduction [derived].
- Later native observation [stated]: on 2026-11-16 JST a fresh, temporarily instrumented app reached the Recording state and displayed the selected-microphone message. Esc then returned it to Ready with a cancellation message. No evaluation audio was replayed and no insertion result was measured. The temporary fixed-stage trace was removed before publication.
- Current verification [stated]: no production audio fix has been applied. The native probe is restricted to the explicitly named virtual cable, forbids default-device fallback, and writes no WAV. The initial HRESULT's cause remains unresolved; the later successful start does not establish a fix.
- Closure decision [decision]: on 2026-11-17 JST the user explicitly accepted #87 verification as complete. Keep the failed attempts and unconfirmed cause as historical evidence rather than inventing a successful insertion measurement. They no longer gate #87 closure under that instruction.
