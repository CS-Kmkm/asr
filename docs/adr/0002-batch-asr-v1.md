# ADR-0002: v1 ASR処理方式 — 録音停止後の一括認識

## ステータス

採用済み (2026-06-13)

## 文脈

音声認識の処理タイミングには主に以下の方式がある。

1. **録音停止後の一括認識 (batch)**: ユーザーが停止を指示してから全音声を一度にASRへ送る
2. **逐次確定ストリーミング (streaming)**: 録音中にチャンクを随時ASRへ送り、
   確定テキストを順次出力する
3. **録音中チャンク先行転写+停止時確定 (hybrid)**: 録音中にチャンクを先行転写して
   中間結果を表示するが、最終テキストは停止時に全音声で確定する

v1設計において、どの方式を採用するかを決定する必要があった。

## 決定

**v1はオプション1(録音停止後の一括認識)を採用する。**

- ユーザーが停止ホットキーを押した後、録音済みのWAVファイル全体をJSONLワーカーへ送信する
- ASR結果が返ってきてから挿入処理を開始する
- 録音中はフローティングUIに「録音中」状態のみを表示する

逐次確定ストリーミング (オプション2) はv1では扱わない。

## 結果

### 採用によるメリット

- **実装がシンプル**: ワーカープロトコルが request/response の1往復で完結し、
  部分結果のストリーミング管理が不要
- **認識精度が高い**: モデルが全音声を一度に参照できるため、
  発話前後の文脈を活用した認識が可能
- **既存VibeVoiceバックエンドとの整合**: VibeVoice-ASR-HFは一括入力を前提とした
  アーキテクチャであり、自然なマッピングになる

### トレードオフ

- 停止後から結果表示までの全遅延がASR処理時間に依存する。
  長文発話では体感遅延が大きくなる可能性がある。
- 処理中に中間テキストが表示されないため、ユーザーは処理完了まで待つ必要がある。

### Phase 1.5 検討事項: 録音中チャンク先行転写

v1完成後のPhase 1.5として、オプション3(hybrid方式)を検討する。

具体的には以下の構成を想定する。

- 録音中に一定間隔(例: 3〜5秒ごと)で中間チャンクをワーカーへ送信し、中間テキストをUIに表示する
- 停止時に全音声を再度送信して最終テキストを確定し、中間結果を置き換える
- ワーカープロトコルは request/response のままで実現可能(中間と最終で2回リクエスト)

この方式では逐次確定ストリーミングの複雑さを避けつつ、
処理中の視覚フィードバックを改善できる。ただし、以下の点を事前に検証する必要がある。

- チャンク分割によるASR精度の劣化(文中で切断された場合)
- 中間転写と最終転写の一貫性
- ワーカープロセスの並列リクエスト処理能力

### 不採用: 逐次確定ストリーミング (v1)

v1で逐次確定ストリーミングを実装しない理由は以下のとおりである。

- ワーカープロトコルをストリーミング対応に拡張する必要があり、設計コストが高い
- VibeVoice-ASR-HF等の大規模モデルはストリーミング向けに設計されていない
- Phase 0でのKPI達成(3秒発話でp50 < 1.5秒)はbatch方式でも達成可能と考える
- 逐次確定の複雑さよりも、まず日常利用可能な安定性を優先する
