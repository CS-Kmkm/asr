# 既存AI音声入力プロダクト調査・機能検証メモ

## 1. ドキュメントの位置づけ

このドキュメントは、Windows向けローカルAI音声入力OSSを設計するにあたり、既存プロダクトの公開情報から機能要件・UX要件・差別化ポイントを抽出するための調査メモである。

本ファイルは、実装計画本体から意図的に分離している。実装計画本体では、競合・既存プロダクト名を出さず、作るべきプロダクト仕様のみを扱う。

## 2. 調査対象

ユーザー指定の以下のプロダクト名を対象とした。

- Amical
- Superwhisper
- Typeless
- Aqua Voice

表記ゆれとして、入力中の `Amucal` は `Amical`、`Aqauavolice` は `Aqua Voice` と解釈した。

## 4. Amical

### 4.1 公開情報上の特徴

AmicalのGitHub READMEでは、ローカルファーストのAIディクテーションアプリとして説明されている。音声認識にWhisper、テキスト処理にOSS LLMを利用し、アクティブアプリに応じて文脈対応の整形を行うとされている。また、音声マクロ、カスタムワークフロー、Ollama、MCP、ローカルAIに関連するトピックも示されている。

公式サイトでは、Mac、Windows、iOS、Android向けの音声入力、アプリに応じたトーン調整、スマート整形、自動修正、プライバシーを訴求している。

### 4.2 抽出される要件

- OSSであること自体が価値になる。
- ローカルファーストは主要な差別化軸になる。
- ASR単体ではなく、LLM整形と組み合わせる必要がある。
- アクティブアプリを検出して出力文体を変える機能が重要。
- 音声マクロやMCP的な外部操作は高度機能として有効。
- Whisper系ASRやOllama系LLMを分離して扱う設計が必要。

### 4.3 実装計画への反映

- `Transcriber`、`TextProcessor`、`TextInjector` を分離する。
- アプリ別プロファイルをPhase 1からデータ構造として用意する。
- Phase 2でローカルLLM整形と辞書連携を実装する。
- Phase 3でプラグイン機構、音声コマンド、外部操作を扱う。

## 5. Superwhisper

### 5.1 公開情報上の特徴

Superwhisper公式サイトでは、macOS、Windows、iOSに対応し、任意アプリでの音声入力、オフラインおよびクラウド音声認識、100以上の言語、Custom AI Modes、独自APIキー、ローカル/クラウドAIモデルの利用を訴求している。

App Store上の説明では、hold-to-record、release-to-paste、句読点、AI formatting、メール・Slack・コードプロンプトなど用途ごとの出力調整が説明されている。

### 5.2 抽出される要件

- 任意アプリへの入力が中核UXになる。
- ホットキーまたは押下中録音の操作感が重要。
- 「録音して貼り付ける」までの体感遅延が価値を左右する。
- Custom Modesに相当する整形プロファイルが必要。
- ローカルモデルとクラウドAPIを選択できる設計が期待される。
- BYO APIキーを扱う場合は安全な認証情報保存が必要。

### 5.3 実装計画への反映

- グローバルホットキー、トグル録音、押下中録音を設計上サポートできるようにする。
- 挿入方式をUI Automation、Clipboard、SendInputの多段フォールバックにする。
- 整形モードをプロファイル化する。
- Cloud LLM/ASRはOpenAI互換APIとして抽象化する。
- APIキーはWindows Credential Managerへ保存する。

## 6. Typeless

### 6.1 公開情報上の特徴

Typeless公式サイトでは、自然発話を洗練されたメッセージ、メール、ドキュメントへリアルタイム風に変換することを訴求している。公開情報上、個人辞書、アプリ別トーン、翻訳、選択テキスト編集、ローカル履歴管理、プライバシーなどが主要な特徴として扱われている。

Google Playの説明でも、自然発話から明瞭で洗練された文章を生成し、タイピングより高速であることを訴求している。

### 6.2 抽出される要件

- 完成形は「ASR」ではなく「音声で文章を作るアシスタント」である。
- フィラー除去、繰り返し除去、口語から書き言葉への変換が必要。
- 個人辞書は中核機能であり、後付けでは弱い。
- アプリ別トーンが実用上重要。
- 選択テキスト編集は高度機能だが、最終形では必須に近い。
- 翻訳は音声入力プロダクトの自然な拡張になる。

### 6.3 実装計画への反映

- ユーザー辞書テーブルをPhase 1から設計する。
- Phase 2でアプリ別プロファイルとLLM整形を実装する。
- Phase 3で選択テキスト編集、翻訳、個人文体プロファイルを実装する。
- ASR原文とLLM整形後テキストを分離保存し、再整形可能にする。

## 7. Aqua Voice

### 7.1 公開情報上の特徴

Aqua Voice公式サイトでは、任意アプリで使える高速音声入力、開発者向け語彙、画面上の文脈理解、コード構文やライブラリ名の認識を訴求している。iOS版の公開情報では、低遅延、新モデル、Voice Edit Mode、現在選択中または直近の文字起こしに対する音声編集が説明されている。

Product Hunt上の説明では、任意のテキストボックス、Cursor、Gmail、Slack、ターミナルなどで利用でき、起動や挿入の低遅延が訴求されている。

### 7.2 抽出される要件

- 低遅延は競争力の中核である。
- 開発者用途では、技術語彙、コード、CLI、ライブラリ名の保護が重要。
- 画面文脈を辞書のように使う設計は強力だが、プライバシー設計が難しい。
- 音声編集モードは高度UXとして有効。
- カスタム指示やカスタム辞書は、ユーザーごとの出力品質向上に直結する。

### 7.3 実装計画への反映

- 技術文書・コードモードを独立した整形モードにする。
- URL、数字、コード、API名、ファイルパス、固有名詞を保護スパンとして扱う。
- 選択テキスト編集はPhase 3で実装する。
- 画面文脈取得は初期版ではアクティブアプリ名・ウィンドウタイトル・選択テキストに限定する。
- 画面全体OCRやスクリーン理解は初期版では扱わない。

## 8. 競合調査から見た必須要件

既存プロダクトの公開情報から、以下はユーザー期待値として必須に近い。

| 項目 | 重要度 | 理由 |
|---|---:|---|
| 任意アプリへの入力 | 高 | 音声入力ツールの基本価値 |
| 低遅延 | 高 | 体感品質を決定する |
| ローカル処理 | 高 | プライバシー・OSS文脈で重要 |
| クラウド任意利用 | 中 | 高精度・利便性を求めるユーザー向け |
| アプリ別プロファイル | 高 | メール、チャット、コードで文体が異なる |
| 個人辞書 | 高 | 固有名詞・専門用語に必須 |
| カスタム指示 | 中〜高 | 上級ユーザーの品質改善に有効 |
| 選択テキスト編集 | 中 | 完成形では重要だがMVPでは後回し |
| 翻訳 | 中 | 音声入力の自然な拡張 |
| 音声コマンド | 中 | 操作系への拡張に有効 |
| 履歴管理 | 中 | 再コピー・再整形に便利だがプライバシー配慮が必要 |

## 9. 差別化方針

既存プロダクトを踏まえると、本OSSの差別化は以下に置くべきである。

### 9.1 Windows入力品質

Windowsは、IME、Electronアプリ、管理者権限、UI Automation対応差、クリップボード挙動などの変数が大きい。ここを丁寧に検証し、アプリ別の挿入成功率を公開することで差別化できる。

### 9.2 評価基盤

CER/WERだけでなく、以下を継続計測する。

- 停止後から挿入完了までの時間
- p50/p95遅延
- 固有名詞正解率
- LLMによる保護スパン改変率
- アプリ別挿入成功率
- VRAM使用量
- ローカルモードでの外部通信有無

### 9.3 プロバイダー交換性

ASR、LLM、挿入方式を差し替え可能にすることで、モデルや実行環境の変化に追従しやすくなる。

### 9.4 透明なプライバシー設計

履歴保存、音声削除、クラウド送信、APIキー管理、ログサニタイズをユーザーに明示し、設定で制御できるようにする。

### 9.5 開発者・技術文書向けモード

日本語・英語・コード・CLI・API名・ライブラリ名が混在する入力を保護することで、一般的な音声入力より開発者向けに強くできる。

## 10. 本体実装計画への反映一覧

| 既存プロダクトからの示唆 | 本体計画での反映先 |
|---|---|
| 任意アプリで使える必要がある | TextInjector、多段フォールバック、Windows連携テスト |
| アプリ文脈に応じた整形が必要 | アプリ別プロファイル、ContextService |
| 個人辞書が重要 | dictionary_entries、辞書UI、ASR/LLM連携 |
| カスタム指示が必要 | プロファイル別prompt_template |
| 技術語彙を守る必要がある | コード・技術文書モード、protected span |
| 低遅延が重要 | Phase 0のp50/p95測定、軽量ASRプロバイダー |
| クラウド/ローカル切替が必要 | Local LLM、OpenAI互換API、明示opt-in |
| 音声編集が将来重要 | Phase 3の選択テキスト編集 |
| プライバシーが重要 | 外部送信既定無効、Credential Manager、ログサニタイズ |
