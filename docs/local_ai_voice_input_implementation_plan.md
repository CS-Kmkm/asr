# Windows向けローカルAI音声入力OSS 実装計画・要件定義

## 1. ドキュメントの位置づけ

本ドキュメントは、Windows 11上で動作するローカルAI音声入力OSSアプリの要件、設計方針、実装計画、評価基準を整理するための実装計画書である。

本体ドキュメントでは、競合・既存プロダクト名を前提にした機能比較や検証は扱わない。既存プロダクトの機能調査・示唆・参照情報は、別ファイル `existing_voice_input_tools_review.md` に分離する。

## 2. プロダクト概要

### 2.1 目的

Windows 11上で、グローバルホットキーを押して話し、ローカルASRで文字起こしし、必要に応じてLLMで整形したうえで、現在の入力欄へ挿入するOSSアプリを開発する。

本プロダクトは、単なる文字起こしツールではなく、以下を統合した「AI音声入力レイヤー」を目指す。

- OSレベルの音声入力
- アプリ文脈に応じた文章整形
- 個人辞書・固有名詞辞書
- ローカル優先のプライバシー設計
- ASR、LLM、入力挿入方式を差し替え可能な拡張設計
- ユーザーごとのマイク環境、語彙、文章スタイルへの明示的な調整

### 2.2 優先プラットフォーム

- Windows 11を最優先対象とする。
- Windows 10対応は可能であれば検証対象に含めるが、保証対象はWindows 11を優先する。
- 初期版ではmacOS、Linux、モバイルOSは対象外とする。

### 2.3 想定ハードウェア

- NVIDIA GPU搭載PC
- VRAM 12GBから16GBを主要検証対象とする。
- CPUのみの実行は、初期版では必須保証対象にしない。
- ASRとローカルLLMを同時利用する場合、VRAM競合が発生するため、モデル常駐・アンロード・キュー制御を設計に含める。

### 2.4 対応言語

初期保証対象は以下とする。

- 日本語
- 英語
- 日本語・英語の混在発話

その他の言語は、ASRモデルやLLMモデルの能力に依存する追加対応とし、初期版の品質保証対象には含めない。

## 3. プロダクト原則

### 3.1 ローカル優先

初期設定では、音声、認識結果、選択テキスト、アプリ文脈を外部送信しない。クラウドAPI利用は明示的に有効化された場合のみ許可する。

### 3.2 交換可能性

以下の構成要素はプロバイダー方式で差し替え可能にする。

- ASRエンジン
- LLM処理エンジン
- 入力挿入方式
- VAD
- モデル管理方式
- クラウドAPIプロバイダー

### 3.3 忠実な文字起こしと文章整形の分離

ASRは発話内容をできるだけ忠実にテキスト化する責務を持つ。LLMはその後段で、フィラー除去、句読点、改行、文体、誤変換修正を行う。

ASRとLLM整形を分離することで、認識誤りと整形誤りを切り分けて評価できるようにする。

### 3.4 明示的な個人化

個人辞書、固有名詞、文体、アプリ別プロファイルはユーザーが明示的に保存・編集できる設計にする。

音声データからの自動学習、声質モデルの自動適応、暗黙の文体学習は初期版では実装しない。

### 3.5 安全な挿入

テキスト挿入は、対象アプリ、入力欄、権限、パスワード欄、IME状態を考慮して安全に実行する。失敗時は無理に挿入せず、クリップボード保持と通知にフォールバックする。

## 4. スコープ

## 5. 機能要件

## 5.1 基本ディクテーション

### R-001: グローバルホットキー

- ユーザーが任意のグローバルホットキーを設定できる。
- ホットキーは録音開始・停止に利用する。
- 押下中録音、トグル録音の両方を将来対応可能な設計にする。
- ホットキー競合を検出し、設定画面で警告する。

### R-002: マイク入力

- 使用するマイクデバイスを選択できる。
- 入力レベルをUIに表示する。
- マイク切断時は録音を停止し、ユーザーへ通知する。
- 録音音声はASR要件に合わせて24kHzモノラルへ変換する。
- オーディオストリームはホットキー押下前からプリアーム(常時開放)またはプリロールバッファを保持し、発話先頭の欠落ゼロを保証する。ホットキー押下から録音開始までの実効遅延はゼロとみなせる設計を目指す。

### R-003: 無音検出

- VADにより無音区間を検出する。
- 短すぎる発話は処理せず、ユーザーへ通知する。
- 無音終了による自動停止は設定可能にする。
- VAD閾値はマイク環境プロファイルとして保存できる。

### R-004: ASR

- 日本語、英語、日英混在発話を認識できる。
- ASRプロバイダーは交換可能にする。
- 高精度・長文向けASRと、短文・低遅延向けASRを分けて評価できる設計にする。
- 固有名詞やユーザー辞書をASRコンテキストへ渡せる場合は渡す。
- ASR結果には、可能であれば以下を含める。
  - 原文テキスト
  - 言語推定
  - セグメント
  - タイムスタンプ
  - 信頼度または代替候補
  - 使用モデル
  - 処理時間

### R-005: テキスト挿入

- 認識または整形済みテキストを、現在の入力欄へ挿入する。
- 挿入方式は以下の順で検討する。
  1. UI Automationによる直接挿入
  2. 一時クリップボード + paste
  3. Unicode入力イベント
  4. クリップボード保持のみ
- 挿入に失敗した場合、生成結果をクリップボードへ保持し、通知する。
- 元クリップボードを復元するか、生成結果を残すかは設定可能にする。
- パスワード欄、管理者権限アプリ、セキュア入力欄では誤挿入を防ぐ。
- クリップボード方式を使用する際は、Windowsクリップボード履歴(Win+V)および
  クラウドクリップボード同期の対象から挿入用一時データを除外する。
  具体的には `ExcludeClipboardContentFromMonitorProcessing`、
  `CanIncludeInClipboardHistory`、`CanUploadToCloudClipboard` の各フォーマットを
  偽に設定して書き込む。これにより音声認識テキストが履歴やクラウドに漏れることを防ぐ。

### R-006: フローティングUI

- 録音中、処理中、完了、エラー状態を視覚的に示す。
- 処理中はASR中、LLM整形中、挿入中のどの段階かを表示できる。
- ユーザーの作業を妨げない位置とサイズにする。
- EscキーまたはUI操作でキャンセルできる。
- **設計注記**: キャンセル時、JSONLワーカープロセスはcancel操作に直接対応していない。
  現在の実装では、キャンセル信号を受け取ったRust側クライアント(`JsonlTranscriber`)が
  進行中リクエストを放棄し、ワーカープロセスをkill → 再spawn → モデル再ロードする
  リセットシーケンスを実行する。キャンセル応答性とモデル再ロードコストのトレードオフを
  考慮した設計が必要である。

### R-007: トレイ常駐

- アプリはトレイに常駐する。
- トレイメニューから以下を操作できる。
  - 録音開始
  - 設定画面を開く
  - 履歴を開く
  - モデル管理を開く
  - 一時停止
  - 終了

## 5.2 AI整形

### R-008: 整形モード

以下の整形モードを定義する。

| モード | 目的 | LLM自由度 |
| --- | --- | ---: |
| 原文重視 | ASR原文をほぼ維持し、最小限の句読点のみ補正する | 低 |
| 自然な文章 | 話し言葉を自然な書き言葉に整える | 中 |
| ビジネスメール | 丁寧な文体、挨拶、改行、敬語を整える | 高 |
| チャット | 短く自然な口調に整える | 中 |
| コード・技術文書 | 技術用語、コード、パス、記号を保護しつつ整える | 低〜中 |
| 選択テキストの編集 | 選択中テキストを音声命令で編集する | 高 |
| 翻訳 | 指定言語へ自然に翻訳する | 高 |

### R-009: ASR原文と整形結果の分離保存

- ASR原文とLLM整形後テキストは別フィールドとして保存する。
- 差分表示できるようにする。
- ユーザーが原文、整形後、再整形結果を選べるようにする。

### R-010: 保護スパン

LLM整形前に、以下を保護対象として抽出する。

- URL
- メールアドレス
- 数字
- 日付
- 時刻
- 金額
- ファイルパス
- コマンド
- コードブロック
- API名
- 変数名
- ユーザー辞書の固有名詞

LLM整形後、保護対象が勝手に変更されていないか検査する。変更が検出された場合は、再試行、原文優先、またはユーザー確認へフォールバックする。

### R-011: LLMプロバイダー

- ローカルLLMを標準とする。
- ローカルLLMはHTTP API経由で呼び出せる設計にする。
- クラウドLLMはOpenAI互換APIとして抽象化する。
- クラウド利用時は、送信内容、送信先、モデル名をユーザーへ明示する。
- クラウド利用は明示的な設定変更がない限り無効とする。

## 5.3 文脈・個人化

### R-012: アクティブアプリ文脈

- アクティブなプロセス名を取得する。
- アクティブウィンドウタイトルを取得する。
- 取得した文脈は、ローカル処理または明示許可されたLLM処理にのみ利用する。
- ウィンドウタイトルは機密情報を含む可能性があるため、ログには保存しない。

### R-013: アプリ別プロファイル

- アプリごとに整形モード、文体、辞書、挿入方式を設定できる。
- 例として以下のカテゴリを内部的に扱えるようにする。
  - メール
  - チャット
  - IDE
  - ブラウザ
  - ドキュメント
  - ターミナル
  - 汎用入力欄

### R-014: ユーザー辞書

ユーザー辞書は以下のフィールドを持つ。

| フィールド | 説明 |
| --- | --- |
| id | 辞書項目ID |
| reading | 読み |
| surface | 正しい表記 |
| category | 人名、社名、製品名、技術用語など |
| aliases | 別表記 |
| priority | 優先度 |
| app_scope | 適用アプリ範囲 |
| created_at | 作成日時 |
| updated_at | 更新日時 |

### R-015: 修正履歴からの候補提示

- ユーザーがASR結果または整形結果を修正した場合、辞書候補として提示できる。
- 自動登録はしない。
- 候補提示のために保存する差分は、履歴保存が有効な場合のみ保持する。

### R-016: 声質・環境調整

初期版では声質モデルの再学習は行わない。代わりに、以下を調整対象とする。

- マイク入力ゲイン
- VAD閾値
- ノイズ環境プロファイル
- 発話前後のプリロール・ポストロール
- ASRプロバイダー選択
- ユーザー辞書
- 整形プロファイル

## 5.4 プライバシー・安全性

### R-017: 外部送信の既定無効

- 初期設定では外部通信を行わない。
- モデルダウンロードはユーザー操作により開始する。
- クラウドAPI利用は明示的に有効化された場合のみ行う。

### R-018: クラウド送信時の明示

クラウドAPIを利用する場合、以下を明示する。

- 送信先
- モデル名
- 送信されるデータ種別
- 音声を送るのか、テキストのみ送るのか
- 保存・保持ポリシーへのリンクまたは説明

### R-019: APIキー管理

- APIキーはWindows Credential Managerへ保存する。
- SQLite、設定JSON、ログには保存しない。
- UI上ではAPIキーをマスクする。

### R-020: 履歴保存制御

- 履歴保存を完全に無効化できる。
- 音声ファイルは処理後削除を既定値にする。
- テキスト履歴の保存期間を設定できる。
- 履歴削除操作を提供する。

### R-021: ログサニタイズ

クラッシュログやローカルログには以下を含めない。

- 音声データ
- ASR原文
- LLM整形結果
- APIキー
- 選択テキスト
- ウィンドウタイトルの全文
- クリップボード内容

### R-022: 権限利用の明示

初回起動時または設定画面で、以下の利用目的を説明する。

- マイク
- クリップボード
- アクティブウィンドウ情報
- Windows UI Automation
- グローバルホットキー
- 自動起動

## 6. 非機能要件

## 6.1 性能

| 項目 | 目標 |
| --- | ---: |
| **ヘッドラインKPI: 3秒発話・warm状態で停止→挿入完了** | **p50 < 1.5秒、p95 < 2.5秒** |
| 10秒発話の停止後から挿入完了まで | p50 < 3秒、p95 < 6秒 |
| 発話先頭の欠落 | プリアーム+プリロールバッファによりゼロ(実効遅延なし) |
| フローティングUI状態更新 | 100ms以内 |
| 履歴一覧表示 | 1秒以内 |
| モデルロード時間 | 計測対象。初回以外は常駐または遅延ロードで最適化 |

ヘッドラインKPI(3秒発話・warm p50 < 1.5秒、p95 < 2.5秒)は日常入力の体験品質を
代表する最重要指標である。Phase 0でこの数値を達成できないASRプロバイダーは
「長文・高精度モード限定」に分類する。

### 計測の分解

性能測定では、以下を個別に計測する。

- 録音終了から音声前処理完了まで
- ASR処理時間
- LLM整形時間
- 保護スパン検査時間
- 挿入処理時間
- 全体時間

## 6.2 信頼性

- ASRワーカーがクラッシュしてもUIプロセスは継続する。
- LLMワーカーがクラッシュしてもASR原文は利用可能にする。
- モデルロード失敗時は代替プロバイダーまたは明示エラーへフォールバックする。
- マイク切断時は録音を停止する。
- GPU OOM時はモデルアンロードまたは軽量モデルへの切替を案内する。

## 6.3 セキュリティ

- 最小権限で動作する。
- 管理者権限での常時実行を前提にしない。
- 管理者権限アプリへの入力は保証しない。
- パスワード欄・セキュア入力欄を検出した場合は挿入しない。
- prompt injection対策として、アクティブウィンドウタイトルや選択テキストをLLM命令として扱わない。

## 6.4 ユーザビリティ

- 録音、処理、挿入の状態が常に分かる。
- 失敗時にユーザーが次に取る操作が分かる。
- 再コピー、再整形、原文利用が簡単にできる。
- 設定項目は「基本」「モデル」「辞書」「プライバシー」「高度な設定」に分ける。

## 7.2 主要インターフェース

以下は言語中立な責務の記述である。Rust側の実際のtraitと、JSONLワーカープロトコルに対応する。

### Transcriber (Rust trait)

```text
Transcriber
  + load(quantization: str) → Result
  + transcribe(audio_path, prompt?, cancel_signal) → Transcript
  + shutdown() → Result

Transcript
  + text: str
  + segments: list[{start, end, speaker?, text}]
  + model: str
  + duration_ms: u64
```

### JSONLワーカープロトコル (stdin/stdout)

リクエスト・レスポンスはすべて1行のJSONオブジェクトで、改行区切りである。

```text
→ {"id": N, "command": "load", "quantization": "4bit"|"8bit"|"bf16"}
← {"id": N, "ok": true, "model": "...", "quantization": "..."}

→ {"id": N, "command": "transcribe", "audio_path": "...", "prompt": "..."?}
← {"id": N, "ok": true, "text": "...", "segments": [...], "model": "...", "duration_ms": N}

→ {"id": N, "command": "shutdown"}
← {"id": N, "ok": true}

エラー共通形式:
← {"id": N, "ok": false, "error": {"code": "...", "message": "..."}}
```

```text
  + capture_target() → Result<TargetWindow>

```

## 9. ASR戦略

## 9.1 基本方針

ASRは単一モデルに固定しない。以下の用途別にプロバイダーを選択できるようにする。

| 用途 | 方針 | 具体候補 |
| --- | --- | --- |
| 短文・日常入力 | 低遅延を優先する軽量ASR | faster-whisper(large-v3-turbo / distil系 / small int8 CPU)、kotoba-whisper、ReazonSpeech、NVIDIA Parakeet系 |
| 長文・議事録 | 長時間音声と構造化結果に強いASR | VibeVoice-ASR-HF、大規模Whisper系 |
| 固有名詞重視 | prompt、hotwords、辞書連携が可能なASR | faster-whisper(initial_prompt)、VibeVoice-ASR-HF |
| GPU制約環境 | 量子化モデルまたは軽量モデル | small int8 CPU、distil-whisper |
| 高精度クラウド任意利用 | 明示許可されたクラウドASR | OpenAI Whisper API等 |

## 9.2 VibeVoice-ASRの位置づけ

VibeVoice-ASRは、長時間音声、話者情報、タイムスタンプ、カスタムホットワード、多言語処理に強みを持つASR候補として扱う。

ただし、日常入力に必要な短文・低遅延性能は実測で判断する。初期設計では、VibeVoice-ASRを唯一の主ASRに固定しない。

## 9.3 ASR評価項目

- CER
- WER
- 固有名詞正解率
- 日英混在発話の保持率
- 数字・記号の正確性
- ASR処理時間
- VRAM使用量
- 初回ロード時間
- warm状態での応答時間
- 辞書あり/なしの改善率
- 雑音環境での劣化率

- 出力が過剰に長くなっていないこと
- JSON出力モードの場合はパース可能であること

## 11. Windows入力挿入設計

## 11.1 挿入方式の優先順位

1. UI Automation
2. クリップボード一時置換 + paste
3. Unicode SendInput
4. クリップボード保持のみ

## 11.2 安全ガード

挿入前に以下を確認する。

- 対象ウィンドウが存在する。
- 対象コントロールが入力可能である。
- パスワード欄ではない。
- セキュア入力欄ではない。
- 管理者権限差により入力できない可能性がある場合、無理に挿入しない。
- ユーザーが録音開始した時点の対象ウィンドウと、挿入時の対象ウィンドウが大きく変わっていない。
- **IMEガード**: 挿入前にIMEが未確定文字列(変換中コンポジション)を保持している場合は
  挿入を保留またはユーザーへ通知し、未確定文字列を破壊しない。
  IME確定後に改めて挿入を試みる、またはクリップボード保持のみへフォールバックする。

## 11.3 クリップボード方針

- クリップボード方式では、現在のクリップボード内容を一時退避する。
- 挿入成功後に元クリップボードを復元するか、生成結果を残すかを設定できる。
- クリップボードに機密情報が含まれる可能性を考慮し、ログには保存しない。
- Windowsクリップボード履歴(Win+V)および Microsoft アカウントによるクラウドクリップボード同期に
  音声認識テキストが誤って記録・同期されないよう、挿入用一時書き込み時は
  `ExcludeClipboardContentFromMonitorProcessing`、`CanIncludeInClipboardHistory`、
  `CanUploadToCloudClipboard` の各フォーマットを偽値で登録する(R-005参照)。

## 12.2 スキーマバージョニングとマイグレーション方針

- SQLiteの `PRAGMA user_version` を用いてスキーマバージョンを管理する。
- アプリ起動時に `user_version` を確認し、現在のコードが期待するバージョンと
  一致しない場合はマイグレーションスクリプトを順次適用する。
- マイグレーションは番号付きの冪等なSQLスクリプトとして管理し、
  バージョンをインクリメントしながら適用する。
- 後方互換性を壊すスキーマ変更(カラム削除、型変更等)は必ずメジャーバージョンとして扱い、
  ユーザーへのデータバックアップ案内を伴う。
- テスト環境では in-memory SQLiteを使用してマイグレーションの正当性を自動検証する。

7. クラウド利用は明示的な opt-in とする。

9. アプリフレームワークはTauri 2 + Rust + React(WebView2)を採用した(ADR-0001参照)。
10. Pythonサイドカーの配布方式は2026-06-13時点で未決定である(ADR-0003参照)。

## 付録A: 検討済み・不採用構成 — PySide6 + PyInstaller

本付録は、旧設計で検討していたスタックを記録目的で残すものである。
現在の実装では採用されていない。

### 旧§8 技術構成案(旧版)

| 領域 | 旧案 |
| --- | --- |
| Desktop UI | PySide6 |
| Windows連携 | pywin32、Windows UI Automation |
| 音声取得 | sounddevice |
| 音声ファイル処理 | soundfile |
| VAD | Silero VADまたはWebRTC VAD |
| ASR | Transformers対応ASR、軽量ASRプロバイダー |
| 量子化 | 4bit標準、8bit/BF16選択可能 |
| ローカルLLM | ローカルHTTP API経由 |
| クラウドLLM | OpenAI互換APIとして抽象化 |
| 設定・履歴・辞書 | SQLite |
| 認証情報 | Windows Credential Manager |
| ログ | ローテーション付きローカルログ |
| 配布 | PyInstallerベースのWindowsインストーラー |
| モデル配布 | インストーラー同梱せず、初回起動時に選択・ダウンロード |

### 不採用理由

1. **プロセス分離の困難さ**: PySide6では、UIプロセスとASRワーカープロセスを
   明確に分離する設計が複雑になる。Tauri + Rustはメインプロセス/サイドカーの
   分離が自然な構造として実現できる。

2. **低遅延キャプチャ**: sounddeviceはPythonのGILを通じた処理になるため、
   低レイテンシのオーディオキャプチャとリアルタイムレベルメーターに
   不利である。cpal (Rust)はWASAPIをネイティブに扱い、
   CPUオーバーヘッドが小さい。

3. **配布サイズと複雑性**: PyInstallerはPython環境全体を同梱するため、
   インストーラーサイズが大きくなる。Tauriのメインプロセスはコンパクトな
   Rustバイナリであり、Pythonランタイムの同梱は
   ASRワーカー部分のみに限定できる。

4. **Windows API統合**: pywin32はWindows APIのラッパーとして十分だが、
   Rustの `windows` クレートは型安全なバインディングを提供し、
   UIAのCOMインターフェースや整合性レベルチェック等の
   低レベル操作をより安全に記述できる。

5. **WebView2 UI**: PySide6のウィジェットより、WebView2上のReactの方が
   Web開発者にとって参入障壁が低く、フローティングUIのアニメーション等の
   実装も容易である。
